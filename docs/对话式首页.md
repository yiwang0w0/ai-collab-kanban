# 对话式首页(第 1 批:服务端)

操作者在首页像聊天一样说要做什么,协调线回一份计划,人看过、改过,按下「按计划建卡」才建卡。
这份文档写服务端的接口与安全边界;面板的版式见 `docs/style-guide.md`。

## 一轮怎么跑

一条用户消息 = 协调线一轮 = 看板起一次 Claude CLI(订阅登录)。同一对话同一时刻只跑一轮。

- 首轮带 `--session-id <看板预分配的 UUID>`,之后 `--resume` 同一个会话;除提示词与会话参数外,每轮参数逐字相同
  (续接不记启动参数,参数一变前缀缓存整段失效)。对话建立时记下模型与强度,之后各轮沿用。
- 每轮的输入 = 看板摘要(各实现线的运行状态与未完成卡数、未完成的目标标题)+ 当前最新计划 + 用户消息。
  摘要与计划标为资料;人改过的字段注明「人改过」,已停用的卡注明「已停用」。
- 输出经 `--json-schema` 交回,服务端只读结果里的 `structured_output`:
  `{reply, title?, plan: null | {goal:{subject,description}, tasks:[{subject,summary,description,acceptance,line,after,needs_confirm,needs_bash}]}}`。
  不从正文里抠 JSON。
- 服务端再查一遍语义:1〜8 张、字数上限、`after` 只能指向排在前面的卡。通过才生成计划版本;不通过不生成,
  原因写进这一轮的 system 消息(`kind:"plan_rejected"`)。线名不在实现线里的,原样留在计划上,建卡时降级。
- 交回的计划没过上面的检查、或有线名不在实现线里:同一轮里再起一次 CLI(`--resume` 同一会话,内容是一段 `[看板检查]`,
  列出问题与可选的线),请它就地修正,只一次。修正那一次交回了计划就以它为准再查一遍,仍不过才记 `plan_rejected`
  (原因后注明已修正过一次);它超时、出错或没给计划时退回首次的结果照常处理;被停止就按停止收尾。
  这一轮的用量、工具数按两次合计记在一条协调线消息上,账本也只记一行(注明含一次修正);每次调用各有 `timeout_sec` 的时限。
- 超时(默认 420 秒)或被停止时收掉整棵进程树。失败时对话 `status:"failed"`,`error` 写原因;再发一条消息就是重试。
  也可以带 `retry_of` 重试失败的那条:不追加消息,用它的原文再跑一轮(见「接口」)。
  首轮没成功过就失败或被停止的,下一条消息换新会话号从头开始,并把没得到回复的消息一并带上。
  续接不到会话记录时不另开新会话(那样会丢上文而人不知道),对话停在失败。
- 每轮的用量(费用、四类词元、内部轮数、时长)记在协调线消息上,并累计到对话的 `usage`;未知的项是 `null`,不记成 0。
- 看板重启时还在跑的一轮标为失败;看板停止或重启前先收掉在跑的协调线进程。

配置(`fleet.config.json`,都可省):

```json
"coordinator": { "model": "claude-opus-5", "effort": "high", "timeout_sec": 420 }
```

`model` 缺省取 `decompose_models[0]`(即 `claude-opus-5`),`effort` 缺省 `high`,`timeout_sec` 缺省 420。写了但写错,看板拒绝启动。
缺省值的依据是 2026-11-10 的两轮拆解评测:`claude-opus-5/high` 质量最好(验收可检查一项满分),单轮最长 265〜356 秒,haiku、sonnet 不够。

用哪个 Claude CLI:协调线与一键拆解、上下文压缩共用 `core/config-setup.mjs` 的 `resolveClaudeCli`,规则同执行线。
`WORKER_CLAUDE_CLI` 写了就以它为准;否则走 PATH,PATH 上只有 npm 的 `.cmd` 包装器时改用它旁边的原生可执行文件
(`node_modules/@anthropic-ai/claude-code/bin/` 下,或与包装器同目录)。`.cmd` / `.bat` 不直接启动;找不到可启动的文件时
`GET /api/coordinator` 给 `available:false` 和怎么改的说明。

## 安全边界

- **只认操作员**:面板会话或操作员令牌。执行令牌、审阅令牌、执行者令牌 403;批准令牌本机接口不认;远程入口不开放这些路径。
- **协调线只读**:`--tools Read Glob Grep`、`--permission-mode dontAsk`、`--setting-sources ""`、`--strict-mcp-config`、
  `--disable-slash-commands`,不给 `--allowedTools`(不带路径的 `Read` 放行规则等于任意路径可读);写工具、执行工具、联网工具另被显式拒绝。
  读范围 = 专用空目录(cwd)+ 工作仓(`--add-dir`);数据目录、验证登记簿、全部认证目录按路径拒读。
  这一组与一键拆解相同,见 `core/board-claude-cli.mjs` 与 `SECURITY.md`。
- **协调线拿不到建卡接口和令牌**:环境剔除登记的凭据变量与看板的令牌类变量;它没有网络工具,也没有 MCP。
  建卡只发生在 `POST …/apply`,由人按下;界面上计划与建卡的状态只按服务端记录显示。
- **cwd 是专用空目录**:在系统临时目录下,按数据目录定名,看板重启后不变;起一轮前发现里面有文件就不启动。
- **源码闸**:当前版本没确认时协调线不可用(与执行线同一条规则)。
- 会话文件由 CLI 写在登录用户的 `~/.claude/projects/` 下,与用户自己的会话并列;看板不读也不清理它们。

## 接口

鉴权与现有写接口同一道。错误体 `{error, code?}`;计划检查不过是 `400 {error, issues:[{n, field, message}]}`。

| 接口 | 说明 |
|---|---|
| `GET /api/coordinator` | `{available, reason?, runtime:"claude", model, effort}`。CLI 找不到或当前版本没确认时 `available:false`,`reason` 写给人看 |
| `GET /api/conversations?archived=0\|1` | `{conversations:[…]}`,新的在前 |
| `POST /api/conversations` `{message}` | 建对话并起第 1 轮 → `201 {conversation, turn:{id, status:"running"}}`;协调线不可用 → `409 COORDINATOR_UNAVAILABLE` |
| `GET /api/conversations/:id` | `{conversation, messages, plans}`,计划按版本升序 |
| `POST /api/conversations/:id/messages` `{message}` | `202 {turn}`;正在跑 → `409 TURN_RUNNING` |
| `POST /api/conversations/:id/messages` `{retry_of:<消息 id>}` | 重试失败的一轮:不追加消息,用这条消息的原文再跑,`202 {turn}` 的 `turn.id` 就是这条消息。要求它是这个对话最后一条 user 消息、它之后没有 coordinator 消息、对话 `status:"failed"`,否则 `409 RETRY_NOT_APPLICABLE`;不是正整数 → 400。带 `retry_of` 时不看 `message` |
| `POST /api/conversations/:id/stop` | `{stopped}`:真的停了一轮才是 `true` |
| `PATCH /api/conversations/:id` `{title?, archived?}` | 改标题、归档 |
| `PUT /api/conversations/:id/plans/:rev` `{expected_rev, goal?:{subject?}, tasks:[{n, enabled?, line?, subject?}]}` | 人改计划,出新版本(`author:"human"`)。`:rev` 或 `expected_rev` 不是最新 → `409 PLAN_CONFLICT`;已建卡 → `409 PLAN_APPLIED` |
| `POST /api/conversations/:id/plans/:rev/apply` `{expected_rev}` | 按计划建卡 → `201 {goal_id, task_ids, demoted, needs_release}`;冲突码同上 |

- `conversation`:`{id, title, status:"idle"|"running"|"failed", goal_id, plan_rev, plan_applied, updated_at, last_snippet, error?, usage:{turns, cost_usd, in, out, cr, cc}}`。
- `messages[]`:`{id, role:"user"|"coordinator"|"system", text, created_at, tools:{count, summary}|null, plan_rev, kind}`。
  `turn.id` 就是那条用户消息的 `id`。system 消息的 `kind`:`applied`、`stopped`、`plan_rejected`、`plan_ignored`。
- 计划:`{rev, author, base_rev, created_at, goal, tasks:[{n, …, enabled, edited}], applied:null|{at, by, goal_id, task_ids}}`。
  消息与计划版本只追加(库层触发器挡改写与删除)。
- 一条消息最多 4000 字(提示词随命令行交给 CLI,Windows 命令行有长度上限)。
- 事件:`/api/events` 推 `{type:"conversation.changed", id}`,只表示「该刷新了」。
  版本确认时推的 `code.accepted` 面板也当成「该刷新了」:协调线能不能用跟着变,对话区立即重读。

## 人改与建卡

- 人只能改 `enabled`、`line`、`subject` 和目标标题;改过的字段记进 `edited`。`line` 只能取实现线或 `null`。
  协调线之后给出的新计划整份替换上一版:`edited` 清空、全部启用。第 1 批由提示词要求它保留人改过的值、不放回已停用的卡,服务端不强制。
- 建卡在一个事务里:目标卡 + 启用的子卡 + 建卡标记 + 一条 system 消息(`kind:"applied"`,写目标卡号与子卡号)。
  同一对话只成功一次(建卡标记是带前态条件的写入)。
- 子卡复用一键拆解的建卡段(`createPlanChildren`):`after` 序号换成卡号;线名不在实现线里降为「不指定线」并进 `demoted`;
  依赖指向已停用的卡时那条先后关系不带,system 消息里写明。
- 目标卡建好即放行,子卡建好即可领(祖先没放行时子卡一张都领不到)。
- `needs_confirm` 的子卡例外:建好不放行,不挂人工闸,卡面注明「要操作者确认后放行」;卡号列在响应的 `needs_release` 里,
  system 消息也写明是哪几张。操作者用现有的放行接口(`POST /api/tasks/:id/release`)放行后线才领得到。
- 已建卡的对话还能继续聊;协调线再给计划不记版本(`kind:"plan_ignored"`)。要再拆一批,开新对话。

## 建卡之后

建卡之后,子卡的进展回流到建卡的那个对话(公告板 v3 合同 B「流转」,实现在 `core/flow.mjs`)。

- `GET /api/conversations/:id` 的 `conversation.progress`:没建卡的对话是 `null`;建过卡的给
  `{goal_id, total, done, items:[{id, n, subject, line, status, waiting_for, released, step, started_via, worker, runtime, handed_back, live_note, live_note_at, updated_at}]}`。
  `items` 是目标下的直接子卡(未归档的,加上已完成后归档的),`n` 是计划里的序号(后来另挂上去的卡为 `null`)。
  目标卡的任务对象另带 `children_done` / `children_total`,与 `done` / `total` 同一口径;首页右栏按目标归组的 d/n 读它。
  `step` 与面板侧栏的五步条同义:0 未放行、1 等领取(已放行)、2 已领取(这一轮还没有启动记录)、
  3 已启动(受管执行线:这一轮有 `process_started`;外部执行者(凭码/令牌接入):这一轮领取之后有过一次心跳)、4 已回传(等待中:待验收 / 待决定 / 等子卡…)、5 完成。
  `started_via`:step 3 的依据,`"process"` = 看板观察到进程启动,`"self_report"` = 外部执行者领取后心跳过(对方自报,面板写「在做 · 对方自报」),其余 null;任务对象另有 `self_reported_started_at`(这一轮第一次执行者心跳的时刻,侧栏「启动」一步取它;受管线恒 null)。
  `live_note` / `live_note_at` 是执行者心跳带的临时进度(`core/connect.mjs` 的表,只在这一轮执行中有值),面板流转条行下那行字读它。
  每次读都按库里当前的卡重算,所以目标自动完成、自动重开也会反映出来。
- `messages` 里每个对话至多一条 `kind:"progress"` 的 system 消息,紧跟在建卡消息之后,原位更新 `text` 与 `updated_at`,
  例:「1/4 完成 · #12 待验收 · #13 开发 在做」(要人做的排前面,最多列 3 项);外部执行者自报启动的卡写「#13 Zcode 在做(自报)」,与流转条、首页右栏、侧栏的「对方自报」同一口径。
  消息表只追加,这条存在单独的小表 `conversation_progress`(每个对话一行),读详情时按位置并进 `messages`;
  它的 `id` 是字符串 `progress-<对话号>`,不是消息表的序号,不能当 `retry_of`。
- 子卡变化(任何 `task.*` / `goal.*` 事件)→ 对应对话 2 秒后推一次 `conversation.changed`,2 秒里的多次变化并成一次;
  进度没变(心跳、无关字段)不推。看板重启后启动盘点时按库重算一遍,不丢、不重复。
- 卡的历史 `GET /api/tasks/:id/history?limit=100`(1..1000,取最近的 N 条,旧→新)与任务对象上的
  `handed_back`(打回次数,含「通过并附指示」退回原线)、`last_actor`、`last_actor_kind`:由只追加的事件表生成,
  判定表写在 `core/flow.mjs` 文件头。条目的 `summary` 是人话,不含长 ID;打回条目带裁定原文的摘要(去掉路径、反引号里的命令、长串,截断)。
  遮蔽宁可多遮:带空格的 Windows 路径、`/c/…` 与 `/mnt/c/…`、UNC、`%VAR%\` 与 `~用户/`、`file://`,
  以及 `github_pat_` / `ghp_` / `gho_` / `exe_` / `sk-` / `xoxb-` / `xoxp-` / `AKIA` / JWT 三段式与 ≥20 位大小写数字混排串。
  遮蔽函数 `redactText`(不截断)与 `safeText`(遮蔽 + 截断)由 `core/flow.mjs` 导出,别的模块(如 live_note)直接复用。
  任务对象的三项用增量缓存算(每次只扫新事件),列表不按卡扫全量事件。
- 两个接口都只给操作员(面板会话或操作员令牌);执行线、审阅线与执行者令牌 403。
