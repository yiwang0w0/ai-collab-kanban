# 宿主逐卡提交

在 `fleet.config.json` 显式设置 `"host_auto_commit": true` 后，实现写入线由可信宿主逐卡创建本地普通提交。旧配置默认关闭；审阅线、只读工具档不自动提交。开关不给模型新增 Git、shell 或其他工具权限，不推送、不部署。

每次领取之前，宿主先占用实际 Git common 目录中的 `kanban-host-commit.lock`，再严格检查工作仓与索引。Git 出错、已有暂存、未提交或未跟踪文件、另一执行者占用时，停止本线并说明原因，领取请求为零。这些拒绝都发生在领卡之前，宿主先收回自己刚建的锁再停线，原因消除后直接重启本线即可；别的执行者留下的锁不动。正常队列空会释放占用；领取响应丢失时保留占用，人工核实原卡后恢复。

Git 程序在循环启动时解析一次并固定，之后每张卡都用同一份路径并核对程序字节。宿主可以给出 git 可执行文件的绝对路径：`fleet.config.json` 的 `host_git`，或环境变量 `WORKER_HOST_GIT`（环境变量已设时优先，server 起循环时把配置值传下去）；没有配置时只在 `PATH` 的绝对目录里查找，不搜当前目录，Git 子进程另带 `NoDefaultCurrentDirectoryInExePath=1`。解析结果是 `.bat`/`.cmd` 包装器，或者落在工作仓、数据目录之内，本线拒绝启动，不领卡。

这套解析不只用于提交。宿主一侧所有启动 Git 的地方——server（交付闸、版本确认、未提交改动提示）、源码闸、只读规则、循环读工作区状态、巡检、`board.py bless`、`doctor`、`setup`——都不按名字启动 `git`，各进程启动后解析一次，之后只用那个绝对路径：Python 一侧是 `core/git_program.py`，Node 一侧是 `core/git-program.mjs`，规则相同。按名字启动时 Windows 会先看进程的当前目录，而循环的当前目录可能在模型的写放行范围里。解析不出安全的程序时，各处按「测不了」处理（源码闸拒绝、server 打印一行警告并把依赖 Git 的检查视为不可测），不退回按名字启动。

开始时绑定工作仓目录身份、`.git` 指针、实际 Git/common 目录、固定 Git 程序、本检出的 HEAD、索引与进行中 Git 操作状态、本分支引用的指向、配置及 include 来源、有效 hooks 与属性控制文件。每轮模型返回后，先直接检查磁盘控制面，再读取 Git 的 NUL 状态并冻结本轮文件及内容。验证过程中新增的路径、改写的工作文件或暂存区不混入提交；属性文件、配置、hooks 等控制面有任何变化时，不再启动新的自动 Git 命令，保留现场。工作仓须可完整枚举，不支持子模块、隐藏工作区变化的索引标记、有效自定义 filter、不可确定的外部 diff/fsmonitor 等配置；只读路径差异查询关闭外部 diff 与 textconv，不改变普通提交钩子。

同一个仓有多个检出（主检出加 linked worktree）时，只绑定本检出自己的 gitdir（HEAD、索引、`ORIG_HEAD`、`FETCH_HEAD`、进行中操作）和全仓共用且影响本次提交的部分（配置、hooks、`info/`、对象库旁路文件）。引用库全仓共用，不按字节绑定整棵 `refs` 与 `packed-refs`，改为直接读盘核对本分支引用的指向：卡在途时必须仍是领卡时的 HEAD，提交后必须是新提交。别的检出里提交、fetch、建分支、打包引用或合并到一半，不影响本检出的在途卡，也不阻止本线领卡；别的检出改了共用配置或 hooks、挪动了本分支，仍按控制面改变处理。引用库是 reftable 时读不了单条引用，退回按字节绑定整个引用库。占用锁在公共目录，同一个仓同一时间只有一个检出能有在途卡。

索引按文件号与字节绑定，所以宿主一侧的只读 Git 调用都不重写索引：循环组提示词时读工作区状态、源码闸、面板与巡检的 `git status` 一律带 `--no-optional-locks`；`git diff --stat` 不认这个开关，另带 `diff.autoRefreshIndex=false`。`checkout`、`reset` 之后的第一张卡因此不会再因为循环自己读状态而被判成控制面篡改。另外，领卡时在仓已核实干净、控制面尚未绑定的那一刻，宿主让索引的 stat 缓存先落定一次，减少卡在途时别的程序（IDE、提示符插件）跑普通 `git status` 重写索引的机会；这一步是尽力而为，同一秒内刚写过的文件落不定。卡在途时仍不要在同一检出里手工运行会写索引的 Git 命令。

只有模型已在工作仓之外写好证据、调用成功且登记验证通过，才按冻结的字面路径正常 `git add`、`git commit`。提交信息为 `#<卡号> <标题>`，经标准输入交给 `git commit -F -`，卡标题不出现在任何命令行里；没有自动署名，不绕钩子，不制造空提交。配置只覆盖一处：这一次 `git commit` 带 `-c gc.auto=0 -c maintenance.auto=false`，不顺带做自动维护——打包引用、重打包对象改写的是与本卡无关的控制文件，此前会让已经生成的提交被报成控制面篡改；身份、签名、钩子等其余配置照旧，仓库的维护留给操作者或别处的普通 Git 命令。原卡报告追加实际 SHA 与本卡路径；两卡修改同文件会得到两个提交。先红后绿的原会话续修保留原 attempt、session、预算与策略，只在最后一次成功验证后提交一次。

模型跑完也一定提交不了的情况在调用模型之前就拒绝。证据目录落在工作仓之内时（看板仓兼作工作仓、又没有另设 `BOARD_DATA_DIR` 的默认布局就是这样；数据目录被 `.gitignore` 忽略，干净检查看不见它），本线在启动门拒绝，不领卡，提示把数据目录移出工作仓。领到没有登记验证（`verify_cmd` 为空）的卡时不调用模型，原卡转等待并说明原因，占用照常释放，本线继续领下一张。卡带着验证键而登记簿里查不到、或验证没有跑成时，仍是停止自动提交、保留现场转等待。

`git commit` 连同它运行的钩子有单独的时间上限：`fleet.config.json` 的 `host_commit_timeout_sec`（10 到 86400 的整数），或环境变量 `WORKER_HOST_COMMIT_TIMEOUT_SEC`（已设时优先），默认 600 秒，只读查询仍是 60 秒。到时宿主终止这次调用的整棵进程树——转发器后面真正的 git、钩子、钩子里的子进程，Windows 上用作业对象，不只是直接子进程——然后先直接检查磁盘控制面，再核对 HEAD。HEAD 没有前移：报告「提交没有生成」，本卡改动留在暂存区，占用保留。HEAD 已经前移（钩子在提交写入之后才变慢）：继续按父提交、路径、提交信息、工作区逐项核对，全部与本卡一致就按成功交付，原卡报告带 SHA，并写明这次调用超时、被终止的钩子可能没有跑完。进程树被终止后留下锁文件等控制面变化时，不再调用 Git，转人工核实提交是否已生成。

模型失败、验证失败、卡住、中断、钩子拒绝或报告拒收，均保留改动、索引和占用，不 reset、不 stash、不自动重试提交。钩子已经执行后可能生成文件或提交对象，报告会保留实际错误，不能把失败解释成“完全没发生写入”。正常完成原卡报告后才释放占用。

人工恢复时，先停止相关执行者，核实原卡的 run、HEAD、暂存区、未提交文件和锁中记录的 owner/pid/root。确认没有执行者仍在占用后，由管理者处理文件、索引及该仓的锁，再恢复本线。不要仅因进程超时就自动删除残留锁，也不要使用另一个工作树绕过同仓占用。

这是一项默认关闭的完整性拒绝措施，不是文件系统权限隔离。并发占用约束遵守本协议的宿主，不能阻止外部编辑器或具有相同账户权限的程序。CLI 写 `.git` 缺口与认证路径隔离仍由后续安全卡处理；本功能没有初始化安全账户、ACL、安装组件或修改用户凭据。
