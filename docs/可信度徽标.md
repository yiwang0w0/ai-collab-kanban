# 可信度徽标:各档的含义与来历

看板 = 公告板。它不替任何 AI 跑命令;它只登记「谁、在哪份内容上、做了什么检查、结果如何」,再**从这些事实推出**一张卡的可信度徽标。
徽标每次读卡时现算,不存任何一方写进来的值。接口细节见 [接入说明](接入说明.md)「可信(合同 H1–H4)」与 [多执行者协作](多执行者协作.md) 的接口一览。

## 先有指纹,再有一切

每次交付(`outcome:"done"`)都会留下一个**指纹**:

| 字段 | 含义 |
|---|---|
| `base_commit` / `head_commit` | 交付方自报的底提交与交付提交(完整十六进制;可不带) |
| `files` | 交付的文件:相对工作仓的路径 + 该文件在 `head_commit` 里内容的 sha256(≤50 项;可不带) |
| `evidence_sha256` | 交付正文的哈希(看板自己算;不带提交与文件的旧用法也有它) |
| `digest` | 上面几项规范化后的 sha256:**比较用的唯一键**。文件顺序无关;`tree` 与 `verified` 不进 digest |
| `tree` | 看板核出来的 `head_commit` 的树对象 |
| `verified` | `true` 看板在可读的工作仓里核过;`null` 核不了(= 自报);`false` 对不上(交付照收,标 `fingerprint_mismatch`) |

看板核指纹只用只读查询(`cat-file`、`rev-parse`):不检出、不读索引、不触发钩子、不执行仓内任何脚本;提交号先严格校验成十六进制才拼参数,
带超时,继承的 `GIT_*` 环境变量一律清掉。哪些线有「看板可读的工作仓」:受管线 = 看板自己的工作仓;外部线要在线配置里写 `work_repo`(绝对路径),没写就只记不核。

**结论绑指纹**:审阅结论、验证检查、人工验收都记下当时的 digest。同一张卡再交付且 digest 变了,旧的那些就 `stale:true`,不再计入徽标,
并给出 `changed_files`(两次 `files` 的差)—— 供「只重审变了的」。

## 检查项从哪来

| by | 谁写 | 怎么来的 | 进哪一组 |
|---|---|---|---|
| `executor` | 执行者(包括凭码接入的、绑线的、共享 worker 令牌) | `report_result` 的 `checks`;请求里写 `by` 也没用 | **自报** |
| `board` | 看板自己监管的执行线的宿主循环,只认该座席的独立凭据 | 循环在交付前跑过卡上登记的验证键(`verify_cmd`,命令取自看板的验证登记簿) | **已核** |
| `reviewer` | 审阅座席(审阅令牌) | 审阅循环在判读前跑过卡上登记的验证键 | **已核** |

已核的检查绑三样:当前 digest、命令哈希(看板自己读登记簿里那一键的命令算出,不采信调用方)、环境标签。
计数 `evidence_counts` 分 `verified` 与 `self` 两组,各自 通过 / 失败 / 未验证 / 基线已红,不混加。

## 徽标各档

取成立的最高档。指纹对不上(`verified:false`)时一律是 `self_reported`。

| 档 | 成立条件 | 现在实际出不出得来 |
|---|---|---|
| `machine_verified` 机器验证 | 卡有 `required_checks`:每一项都有已核的 ran + pass,且绑当前 digest。卡没有 `required_checks`:至少一项已核实跑、且已核实跑的没有(非基线)失败 | **出得来**:审阅座席跑卡上的验证键并通过;或受管线宿主跑验证键通过。一张卡只有一个验证键,所以 `required_checks` 超过一项时,目前只能由「宿主一项 + 审阅一项」凑齐 |
| `cross_model_reviewed` 另一家审过 | 审阅座席判通过,结论绑当前 digest,审阅方家族 ≠ 写作方家族(两边都要已知) | **出得来**:写作方家族取自受管座席的运行时或凭码接入时的种类;种类「其他」与手登记的执行者 = 未知,不算 |
| `independent_rerun` 独立复跑 | 有已核的 ran + pass(绑当前 digest),但不够机器验证 | **出得来**(主要在「必需检查没凑齐」时) |
| `self_reported` 只是自报 | 其余 | 默认 |

家族:`claude` / `codex` / `zcode`;其余一律未知。

`flags`(弱化标记,不改档位):

- `stale`:有旧指纹上的检查或结论,当前指纹上还没有同名检查 / 同类结论顶上;
- `baseline_red`:当前交付里有「底提交上本来就红」的检查;
- `fingerprint_mismatch`:指纹与工作仓对不上;
- `based_on_stale_spec`:交付基于旧版说明(字段由说明版本确认一侧给出;缺失 = 没有)。

`provenance` 列出推出这一档所用的事实:`{what, by, at, digest}`。

## 基线红

`checks[].baseline:true` 且失败 = 「在底提交上本来就红」。它单列 `baseline_failed`,**不算进** failed;卡上给
`baseline:{ base_commit, red:[{check, by, first_seen_commit}], self, verified }`,显示「基线已红 n 项(自报 / 已核)」。
执行者报的是自报;已核的基线红要由看板或审阅座席在底提交上跑出来 —— **现有的验证路径不在底提交上跑,所以目前出不来**。

## 自动通过的硬闸

只管**自动通过**(线配置 `accept:"auto"` 的交付即完成、审阅座席的通过);人的显式裁定不受限。

- 卡有 `required_checks`:每一项都要有已核的 pass、绑当前 digest;
- 指纹不能对不上;
- 交付不能基于旧版说明。

不满足就不自动通过:`accept:"auto"` 的交付留在待验收;审阅座席判通过的卡盖「审过」印、写明缺什么,转人工验收。没有 `required_checks` 的卡,除上面后两条外规则同以前。

`required_checks` 只由操作者定:建卡时带,或建计划时计划项带;之后只有操作者经 `POST /api/tasks/:id/required-checks` 能改。
执行者、助手、共享 worker 令牌、审阅令牌都改不了。

## 目前还做不到的

- 一张卡只有一个验证键:多项必需检查只能由宿主与审阅各跑一次凑,同名的会互相覆盖为「最近一次」。
- 已核的基线红(在底提交上跑)没有现成路径。
- 看板侧核对只覆盖「线配置了看板可读的工作仓」的情形;外部执行者在自己的克隆里提交而没推到那个仓,会被判对不上。
- 验证命令跑的是工作仓里的测试代码;命令本身取自登记簿,但测试文件来自被测分支 —— 「验证脚本不取自被测分支」目前只做到命令这一层。
