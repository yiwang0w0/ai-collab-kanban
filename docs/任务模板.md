# 执行者任务模板

`summary` 继续写给人看的一两行结果；`description` 写给执行者，按 `goal:`、`ctx(file:line):`、`do:`、`accept(cmd -> expect):`、`limits:` 五段组织。上下文只列本卡必要入口；未核实的位置写“待定位”，不要编造行号。`acceptance` 与 accept 段保持同一命令和预期，说明退出码、断言或产物。

运行 `python cli/board.py create --template` 可离线查看 JSON；也可复制 `examples/任务模板.json`，填写后用 `python cli/board.py create --file task.json` 建卡。模板只使用现有字段，旧 JSON payload 仍原样提交，由服务端按角色白名单取值。普通卡沿用服务端既有放行默认；显式执行配置卡由服务端固定为未放行，核对后再放行。模板不携带放行、尝试次数或人工闸控制；这些操作仍走原有 `hold`、`release`、`edit` 入口。操作者自己在 payload 里写了这三项时，收紧的取值照收：`released: false`（先不放行）、`humanGate: true`（加人工闸）、`maxAttempts` 不大于默认的 3。放宽方向（`humanGate: false`、更大的 `maxAttempts`）建卡时不生效，响应的 `not_applied` 逐项点名，`board.py create` 会打印出来；放宽仍走 `release`、`edit`。取值类型不对（例如字符串 `"0"`）返回 400 并点名字段，不建卡。填写 `verifyCmd` 时仍须使用操作者已登记的验证键。

拆解器及派生卡沿用同样的说明结构。父 run 绑定、重复任务判定、角色权限和放行规则仍按现有流程处理。
