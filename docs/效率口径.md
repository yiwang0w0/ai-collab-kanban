# 效率口径

`GET /api/efficiency` 与 `python cli/board.py efficiency` 回答一个问题:这一期比上一期,AI 帮你多干了多少、返工多少、你花了多少工夫。实现在 `core/efficiency.mjs`(公告板 v3 合同 C 节)。

所有数字都由已经落库的数据算出:`tasks` 表、只追加的事件表 `task_events`、`task_runs`,以及用量账本(见 [用量结算](用量结算.md))。不调用模型,不写库。

## 怎么用

```
GET /api/efficiency                                   # 本周对上周
GET /api/efficiency?from=2026-11-01&to=2026-11-07     # 指定区间;上期 = 紧挨在前面、一样长的区间
GET /api/efficiency?by=day|week|line|runtime          # 另给分解(groups)
python cli/board.py efficiency [--from … --to …] [--by …]
```

- 时区用看板本机的时区。一周从周一零点起算。
- `from` / `to` 只写日期时,`to` 包含当天一整天;写了时刻时,`to` 那一刻不算在内。两个要一起给,区间最长 400 天;`by=day` 时最长 92 天、`by=week` 时最长 2 年(按段数封顶),超出回 400 并写明上限。
- 只给操作员(面板会话或操作员令牌)。执行线、审阅线、执行者令牌回 403,远程批准入口没有这个接口。

返回值的形状见合同:`period` / `previous`(本地时刻带时区)、`now` / `prev` 两组指标、`groups`(按 `by` 分解)、`daily`(本期逐日的新挂与完成;区间内每一天都有一行,没有数据或还没到的日子是 `created:0, done:0`)、`headline`(一句话)。

## 每个数怎么算

| 字段 | 算法 |
| --- | --- |
| `done` | `resolved_at` 落在区间内、**当前状态仍是完成**的卡张数。目标卡(`kind=goal`)不计;下面挂着子卡的父卡也不计,它的工作已算在子卡里。重开后再完成的卡只按最后一次完成算(`resolved_at` 只留最后一次) |
| `lead_ms_median` | 上面这些卡的 `resolved_at − created_at`,取中位数 |
| `cycle_ms_median` | 首次领取事件 → `resolved_at`,取中位数。没有领取事件的卡(旧数据)不进样本 |
| `handed_back` | 区间内的打回事件条数(所有卡,含目标卡) |
| `first_pass_rate` | 完成的卡里,整个生命周期内没有被打回、也没有被重开过的比例 |
| `auto_accept_rate` | 区间内「通过」事件里,由自动审阅通过的比例。联动关闭(父卡通过带走子卡)两边都不计 |
| `human_actions` | 区间内由人做的 裁定 / 放行与收回放行 / 重开 事件数。经面板、操作员令牌或远程批准的都算人 |
| `wait_human_ms_total` / `_median` | 每次人的裁定,往前找这张卡最近一次交付,两者的间隔。按裁定时刻归到哪一期;中间如果是自动审阅「交审阅」,继续等人;自动直接通过或打回的,不算等人 |
| `ai_work_ms` | 各卡持卡时段(`work_spans`)与区间求交后的合计。还在做的卡,最后一段算到现在 |
| `parallel_avg` | `ai_work_ms ÷ 所有时段的并集时长` = 有卡在跑的时候,平均同时有几张在跑 |
| `parallel_peak` | 区间内同时在跑的最多张数(首尾相接不算同时) |
| `model_ms` / `cost_usd` | 账本里时刻落在区间内的行,耗时(模型墙钟)与费用的合计;分解时只算归属到这组卡的行 |
| `stalled` | 区间末尾仍在执行中、心跳超时的卡数(「最近一次活着」取卡心跳与持卡执行者最后一次请求里较晚的,与 `GET /api/executors` 的 stalled 同口径;受管线只看卡心跳)。超时阈值与执行者「卡死」判定同一个(`BOARD_COORD_STALE_MIN`,默认 20 分钟) |

事件归类(哪条算领取、交付、通过、打回,谁算人、谁算自动)直接用 `core/flow.mjs` 的判定表,与卡的「历史」一处定义。

分解:`by=line` 按卡的线;`by=runtime` 按这张卡最后一次执行记录的运行时(`task_runs.runtime`,没有时用卡上的 `last_runtime`);`by=day` / `by=week` 是本期内的时间序列,还没到的日子不列。区间里什么都没发生的组不列。没有线的卡 / 不知道运行时的卡归到 `key: null` 那一组,`label` 是「未指定」。分解只是按线、按执行器摆开看,不排名。

## 哪些会是未知

**未知一律是 `null`,并把字段名放进 `unknown`,不当 0。** 每个为 `null` 的字段都在 `unknown` 里,反过来也一样。

| 情形 | 未知的字段 |
| --- | --- |
| 区间里有派发过(`attempts>0`)却没有 `work_spans` 的旧卡 | `ai_work_ms`、`parallel_avg`、`parallel_peak` |
| 账本在区间里没有行,或有一行缺耗时 / 费用 | `model_ms` / `cost_usd`(没有记账记录不等于没花) |
| 区间末尾已经过去 | `stalled`(看板只存最新一次心跳,不知道当时谁卡着) |
| 没有完成的卡 / 没有通过事件 / 没有人的裁定 | 对应的中位数与比率(0 ÷ 0 不是 0) |
| 没有任何时段 | `parallel_avg` |

能确定是零的就给 0:区间里没有打回就是 `handed_back: 0`,没有人裁定时 `wait_human_ms_total: 0`,没有领取也没有时段时 `ai_work_ms: 0`。

主句里数字未知的那一段直接省略,不写 0,例如 `本周完成 4 张 · 打回 2 次 · AI 干了 10.3 小时 · 你操作 5 次 · 平均同时 1.3 条线在跑`。吞吐和返工总是一起出现。AI 时长的写法:不到 1 分钟写「不到 1 分钟」,不到 1 小时写整分钟(「AI 干了 53 分钟」,向下取整),1 小时起写一位小数的小时;面板首页与 `board.py efficiency` 都原样显示后端给的 headline,不各自另算。

## 为什么不设「人工要多久」的基线

看板里没有「这件事人来做要多久」的数据。拿一个估出来的人工时长去除,得到的「提速几倍」就是编出来的数,还会随估法任意变大变小。所以这里只比 **本期对上期**:同样的口径、同样的数据来源,变化才有意义。要看 AI 帮了多少,看 `ai_work_ms`、`parallel_*` 与 `human_actions` / `wait_human_*` 的此消彼长;要看质量有没有被牺牲,看 `first_pass_rate` 与 `handed_back`。

## 缓存

结果按「事件表最大 id + 卡表签名(条数、最晚更新时刻)+ 账本读到的位置 + 区间 + by」缓存,最多 32 份。区间末尾还没到时再加 30 秒的时间片(进行中的时段与心跳会随时间变)。卡表读出来的快照另按「事件水位 + 卡表签名 + 30 秒时间片」缓存一份:换 from / to 只重算区间里的数,不重读卡表、不重扫事件。2000 张卡 / 2 万条事件:冷算约 0.1–0.2 秒,热读约 1 毫秒;再加 2 万行账本时,`by=day` 92 段约 0.15 秒、`by=week` 2 年约 0.2 秒(每段各查一次账本,是区间上限要封住的那部分)。
