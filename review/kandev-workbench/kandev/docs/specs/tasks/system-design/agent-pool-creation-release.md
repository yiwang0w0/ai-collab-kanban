# 任务池直接创建与批准收尾

## 范围和依据

本文细化[工作台设计](agent-pool-workbench.md)中的创建生命周期，沿用[原生运行权决策](../../../decisions/2026-10-16-agent-pool-native-run-authority.md)和[外部身份幂等契约](external-id-idempotency.md)。不增加表、持久创建状态或调度器。生产池发布／消费构造仍关闭，本文不是功能验收。

## 请求边界

HTTP／WS 原生创建请求接受可选 `pool_release`，共用移动入口的严格解码器。仅接受 `confirm_cli_quota`、`expected_resource_version` 和 `expected_step_version`；直接创建的任务版本必须为空，阶段版本保留原始 RFC3339Nano 字符串。既有浏览器发送器原样保留这些字段，不生成身份、时刻或初始任务版本。

宿主从实际阶段解析固定 Profile，并校验 CLI／Worktree、真人浏览器身份及当前配置。请求选择的执行器写入既有任务元数据后仍须经过原生事务核验；请求值本身不是能力证明。池创建不得同时要求普通 `start_agent`／`prepare_session` 或携带延迟启动意图，不能从共享队列旁路直接启动。无确认的池创建拒绝，普通非池创建保持原行为。

## 原生分段创建

原生 `Repository.createTask` 在卡片插入提交后同步派发阶段进入动作，而服务随后才写依赖、仓库关系和策略；HTTP 还需认领附件、处理 fresh-branch 等必要收尾。因此不能把初次插入账本作为可执行批准。

`Service.CreateTask` 只给初次池插入附加内部 `Creating + DeferCreation` 意图。仓储先执行已有真人／阶段／能力门禁，但不写初始批准账本，不派发阶段回调。任务服务使用原上下文完成后续写入，不让创建批准意图传给依赖事件。阶段／WIP 放置仍由原生创建路径负责。

仅这次真实创建的 `CreateTaskResult` 携带服务私有、内存中的收尾许可，绑定原始卡片版本、阶段快照、外部身份和创建者浏览器。它不是数据库状态、公开接口或恢复凭证，不能从 GET／重连／序列化结果重建。卡片可能已可见，但在批准账本出现前不可视为已发布。

HTTP 在既有必要收尾结束处调用 `CompleteTaskCreation`；WS 对池创建先通过真实附件服务认领文件，再调用同一方法。普通创建沿用原有外部身份结算。两种入口不在池创建旁路启动会话。

## 批准事务和派发

`CompleteTaskCreation` 授权当前任务写操作，并拒绝把原创建许可转移给另一浏览器。它复用 `WithPoolReleaseAdmission`，在共同任务准入中调用 `CommitPoolTaskCreation`：

1. 先取得 SQLite 原生任务写权，核对原任务版本、当前流程／阶段、未结算外部身份及不存在任何已提交进入记录。
2. 再经原生阶段写门禁检查真人确认、固定配置、WIP、依赖、活动运行／会话／回合和执行候选；不推测缺失资料为空闲。
3. 同一事务提交唯一 `pool_release_v1` 账本。带外部身份时，同时写 `external_id_settled_at`；批准或结算任一写入失败都整体回滚。
4. 提交后才调用原生 `dispatchStepEntry`。批准时刻来自本次事务，不使用较早的卡片创建时间。

原生回调的进入身份实际是无前导零的十进制账本 ID。池发布器接受这一格式，也兼容此前固定宽度 `entry:` 拼写；二者都解析到同一个整数来源和稳定派发键。非规范格式、非当前账本、跨任务或跨阶段身份仍拒绝。不能把收到回调或批准成功等同于实际入队：入队证明仍来自持久化的同一 run。

PostgreSQL 不支持这一首版池路径，明确拒绝，不做降级写入。

## 失败、中断与幂等

必要仓库／策略写入失败继续走既有部分创建回滚。附件失败按原生生命周期补偿删除；清理失败会保留未批准卡片并记录错误，不能据此派发。fresh-branch 的原有错误／补偿语义不变；实际 Git 已修改而关联重写失败时，不谎称 Git 已回滚。

原版本或配置变化时拒绝批准，不覆盖并行编辑。外部身份在收尾期间被释放，返回现存卡片但不批准／派发；不能为了通过版本检查重新采用最新卡片快照。已结算或已有阶段记录不能再使用原收尾许可。

外部幂等键的 Found 结果仍在服务最前面短路；入口跳过全部必要收尾和派发，不重放他人的创建流程。请求中断、宿主重启或提交结果不明时不恢复内存许可；缺少批准账本的卡片不能通过普通账本回填、读取或自动重新发布来获得批准。提交异常不触发可能删除已批准卡片的盲目补偿。后续人工核实／恢复仍归原工单，不是本许可的隐式重试。
