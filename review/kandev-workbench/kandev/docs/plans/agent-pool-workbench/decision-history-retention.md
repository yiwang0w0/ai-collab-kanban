## 已验证的缺口

固定基线为 e43881c7555372897b57ec51c705f1e05da43c40 加本目标未提交改动。

新测试位于 `apps/backend/internal/task/handlers/pool_history_retention_test.go`，使用真实任务／工作流／运行 schema、浏览器确认入口、原生发布与不可变领取。所有删除只发生在 t.TempDir 的 SQLite 文件中。终态通过测试元数据构造，不冒充真实模型执行、停止或人工恢复；清理本身则实际调用原生 `retention.Store.CountEligibleRuns` 和 `DeleteRunBatch`，不是直接 DELETE 后模拟结果。

实际观察：

- 同一批准在清理前返回 deduped，原生行数不变，证明发布器和测试入口真实可达。

- 同一批准再次传入真实 PublishPoolRelease 时返回 queued／nil error，运行行数从 0 变为 1。没有启动消费者或模型；此处证明逻辑运行能够被重新创建，不声称已经发生重复模型消耗。

三条回归当前均为有效 RED，缺陷尚未修复。实际结果改变了下一步：仅增加 UI 提示不足以处理被删除的去重依据。

## 已核对的原生接点

`office/retention` 的 run 选择只按终态、年龄、每 Profile 保留底数和暂停恢复引用判定，没有池键豁免；同一事务删除 run_events、路由／技能卫星及 run。`office_launch_ledger` 仍保留不可变 claim ID 和领取时间，但不含任务／阶段派发键，不能按时间猜测归属。

`task_step_transitions` 记录批准、阶段和真人，不记录已派发 run ID 或清理结果。现有 `workflow/stepentry` 明确将 queue_run 归为 ledger-owned、非 marker-bearing；它不能直接充当这条池发布路径的已完成动作回执。普通动作的 marker 所有权和恢复语义不因此改写。

## 若选 A，后续设计必须约束的契约

1. 仍由既有原生维护所有者执行，不增加清理调度器。最小凭证与删除在同一事务提交；凭证失败或不可核验则回滚删除，不能留下“清理成功但防重派依据丢失”。
2. 原生发布事务同时核对活 run 与清理凭证；旧批准命中凭证时返回明确历史已清理／需新批准结果，不创建 run、claim 或会话，不构造虚假的活动 Run 充当 deduped。
3. tasks 在同一权限和最大 50 项边界内批量读取原生凭证，关联仍保留的不可变领取账本。单卡历史、工作区页、原生摘要和共享客户端显示明确清理状态，不能把空行当成从未派发。
4. 清理凭证不是开工证明。只有清理事务核验原生回执且明确保留的事实才能显示；其他时间留空，不从缓存、当前时钟或相似记录补造。存量无关联资料仍待核实，不追认清理时间。
5. 明确凭证格式版本、字段及批次上限、作用域、生命周期、旧数据库迁移／重放、写失败回滚与并发发布／清理的锁顺序；更新对应原生 schema 所有者和验收，不私自引入公开 RPC 或第二份任务状态。
6. 复用既有提交后失效、CAS 重建及完整替换契约，覆盖读取／重连／省略和迟到数据；测量新增有界读取成本，不能通过放松预算断言掩盖 N+1。

这些是选定后的设计输入，不是完整迁移设计或已实施接口；技术决策仍须按 record 规则形成 ADR，并同步所属系统设计后才能实现。

## 若选 B，后续设计必须约束的契约

池记录的豁免必须覆盖原生选择、预览、计数和删除的同一政策来源；普通非池运行的年龄、保留底数和清理集合不能被顺带改写。原生其他删除入口也不能绕过该保护。测试须保留普通运行确实被清理的正对照，证明池去重与领取／开工事实仍在；不得只把本轮 RED 断言改成始终不执行清理。

此选项需要显式修订“池旧证据按现有策略清理”的设计和显示语义，不能暗中删去原清理要求后宣布完成。
