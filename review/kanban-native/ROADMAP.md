# 下一轮路线：增强原 Kanban，不换宿主

此文件冻结方向和开发顺序，不授权切换生产、迁移旧数据或调用真实 CLI／API。每批只解决已经确认的缺口，直接相关测试通过后交付；无新改动或失败时，不重复大套验证。

## 1. 原生能力对照，先判断有没有必要做

从原 Kanban 的状态库、REST／SSE、worker 循环、门禁和面板确认派发、领取、工作记录、父子关系、依赖、审查、人工裁定与恢复的现有契约。将需求分为“已有”“仅缺展示”“需要最小扩展”“需要外部条件”，再确定实施基线与受影响测试。

现有 `released`、`claim`、租约、`attempts`、`work_spans` 等字段不能仅凭名称重新解释：尤其不能把有领取、业务状态进行中或进程存在直接说成模型已经开工。缺少可信来源时显示“待核实”，确有缺口才设计原生扩展，不新建平行任务库或调度器。

## 2. 原面板体验与执行可见性

在原 `core/panel.html` 及其既有设计规范上增量改进，优先呈现“待我处理”和“执行中”，降低默认界面的诊断噪声。借鉴 Kandev 的信息层次、任务详情和快捷切换，不搬入其整套技术栈。

卡片和详情必须清楚区分派发、实际领取、进程启动、可信开工、本轮结束与最终验收；展示时间和执行者时能追溯到原生事实。保留现有卡片 ID、状态含义、历史和权限。前端读取只展示，不补造执行记录或重新派发。

父子、依赖和阻塞关系先复用现有契约，优先补“关系看得见、能够跳转、原因说得清”。不因 UI 好看而新增已有关系模型；人工恢复也先复用现有受控操作，不能因静默或旧心跳自动认定失败并另发任务。

## 3. 全站信达雅中文化

目标是 **原 Kanban 的全部自有界面文案**：菜单、设置、卡片、确认框、危险提示、占位符、悬停说明、空状态、加载／失败／重试、通知和无障碍名称。先盘点已有中文、生硬译文和残留英文，再建立术语表；不只清扫英文，也不把所有词机械替换成中文。

保留品牌、命令、机器字段、协议 ID、路径、用户输入、模型原文及第三方原始日志；必要时加中文说明，不改变原值。统一“智能体、派发、入队、领取、开始执行、待验收、验收通过、待核实”的使用边界，不把它们全部叫作“完成”。

用户提供的 Kandev 截图只作为文风和安全语义的参考，不意味着向原 Kanban 增加该权限开关：

- `Auto-approve all permissions`：自动批准所有权限请求。
- 说明：Kandev 会自动批准智能体发起的所有权限请求，不再逐次询问。此设置存在安全风险，仅可在可信工作区中使用。
- `TUI Passthrough` 可拟为“终端直通模式（TUI）”，但须先核对原系统是否有对应功能及其真实含义。

翻译不得弱化危险提示、扩大权限、改变默认值或省略确认。桌面与手机都要检查换行、按钮可读性、触摸目标和长文；只针对改动页面验证，不为截图开启危险设置。

## 4. CLI／API 后续扩展边界

保留原 Kanban 已有 Claude／Codex CLI 路径和交付门禁，不以 Kandev 执行器替代。API 接入另行形成小范围设计，先检查原适配器、调用回执和用量记录能够复用什么，再补真实缺口；明确凭据、费用、预算和失败处理后，才在授权下验证。

本轮不接 API、不填密钥、不调用真实模型，也不把“可以启动 CLI”当成“已完成真实模型任务”。

## 执行方式与收口

采用“确认一个缺口 → 最小修改 → 直接相关测试 → 独立审阅”的轻量工作流。先完成原生能力对照和小批中文文案，再按实际证据决定是否扩展执行记录；不并行铺开多个未验证的大改造。

新能力实施前提交短小、可审阅的需求／设计／工单；完成一批就交接。只跑受影响测试，既有全量回归交给 CI；CI 失败先判断是否由该批引入，不以扩大实现或反复重跑掩盖问题。复核到足以支撑本批结论即停止，明确保留未完成项。
